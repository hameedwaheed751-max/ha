# تصميم: التجديد الذاتي بالبطاقة لمشتركي RADIUS

> وثيقة تصميم للمراجعة قبل أي كود. التنفيذ على مراحل معتمدة، منفصلة عن دفعة فايبر اكس.
> تاريخ: 2026-11-25 · الفرع المقترح للتنفيذ: فرع مستقل لاحقاً (ليس feature/next-release الحالي).

## 1. الهدف
تمكين مشترك RADIUS من تجديد اشتراكه ذاتياً من تطبيق **مشترك نت**، بالدفع إلى **حساب Qi (ماستر) الوكيل** عبر سوبر كي، على أن يؤكّد الوكيل استلام المبلغ ثم يُفعَّل المشترك على الساس ويُستقطع رصيد الوكيل — دون قدوم المشترك للمكتب.

## 2. النطاق
**داخل النطاق:** مشتركو **RADIUS فقط**.
**خارج النطاق صراحةً:** FTTH (المشروع الوطني)، فايبر اكس، إيرثلنك — لأنها تقبل الدفع بالماستر لخدماتها مباشرةً. لا تظهر لها خطوة الدفع الذاتي.

## 3. القرارات المثبّتة (من المحادثة)
- **الربط:** برمز دعوة يولّده الوكيل (`subscriber-invitations`) — موجود أصلاً.
- **صلاحية المشترك:** تجديد **نفس الباقة فقط** (`allow_package_change = false`).
- **وسيلة الدفع:** تحويل يدوي عبر سوبر كي إلى **رقم حساب Qi للوكيل** (نسخ نصّي). لا باركود (لا يُمسح على نفس الجهاز) ولا رابط عميق (غير مدعوم في سوبر كي).
- **التأكيد:** يدوي من الوكيل بعد رؤية الإيداع (لا تفعيل بلا تأكيد) — حماية من ادعاء الدفع.

## 4. الوضع الحالي (ما هو مبني فعلاً)
بوابة المشترك جاهزة على الأطراف الثلاثة:
- **خادم البوابة** `/api/v1/*` (duckdns) — **مطفأ حالياً**، العقد في `C:\Mushtaraknet\docs\SUBSCRIBER_API.md`.
- **وكيل نت** `lib/services/subscriber_portal_service.dart` — دعوات، روابط، ملخّصات، إعدادات (`show_debt`, `allow_package_change`)، باقات، إعلانات، **طلبات تجديد (قبول/رفض/إكمال/فشل)**، تذاكر دعم، ومزامنة تلقائية (`SubscriberPortalSync`) **تُكمل التجديد آلياً عند تقدّم تاريخ الانتهاء**.
- **مشترك نت** `lib/data/api/api_backend.dart` — ربط، طلب تجديد، مالية، دعم، وحقل `AgentInfo.masterAccount` جاهز للعرض.

**التدفّق اليوم:** طلب تجديد → الوكيل يفعّل بنظامه → «تم التجديد» تلقائياً. **الدفع خارج التطبيق.**

## 5. الفجوة = طبقة تأكيد الدفع فقط
ثلاث إضافات على ما هو موجود:
1. الوكيل يحفظ **رقم حساب Qi** → يظهر للمشترك.
2. المشترك يضغط **«دفعت» + رقم التحويل/وصل** → يُبلَّغ الوكيل وتُسجَّل حالة دفع.
3. الوكيل **يؤكّد الاستلام** → يفعّل RADIUS (المسار الموجود) → إكمال تلقائي.

## 6. المعمارية والتدفّق المستهدف
```
مشترك نت                خادم البوابة /api/v1        وكيل نت (NetAgent)
───────────             ───────────────────         ──────────────────
«جدّد» (نفس الباقة) ──▶ POST subscriber/renewals ──▶ (موجود) طلب pending
يرى رقم Qi + المبلغ  ◀── agent.master_account
يحوّل عبر سوبر كي
«دفعت» + رقم التحويل ─▶ POST renewals/:id/payment-claim ─▶ push للوكيل
                                                        الوكيل يرى الادعاء+المرجع
                                                        يتأكّد من الإيداع
                        POST renewals/:id/payment-confirm ◀── «تأكيد الدفع»
                                                        يفعّل RADIUS (استقطاع رصيد)
«تم التجديد» ◀────────── complete (تلقائي عند تقدّم الانتهاء) ◀──┘
```

## 7. التغييرات التفصيلية

### 7.أ) خادم البوابة (gateway) — Phase 0
- **تفعيل خدمة `/api/v1`** على الخادم (منشورة حالياً لكن مطفأة).
- **`portal-settings`**: إضافة الحقل `master_account` إلى GET/PUT (إلى جانب `show_debt`, `allow_package_change`).
- **حمل `agent` للمشترك**: تضمين `master_account` في كائن الوكيل الذي يراه المشترك (يقرؤه `AgentInfo.masterAccount`).
- **نموذج دفع على الطلب** (`renewal.payment`):
  ```json
  { "method":"qi", "reference":"<رقم التحويل>", "receipt_url":"<اختياري>",
    "claimed_at":"ts", "confirmed_by_agent":false, "confirmed_at":null }
  ```
- **نقطة جديدة (المشترك):** `POST /api/v1/subscriber/renewals/:id/payment-claim`
  Body: `{reference, receipt_image?}` → يملأ `payment` (claimed)، يرسل **push للوكيل**، يعيد `RenewalRequest`. يُرفض إن كان الطلب غير مفتوح أو ادّعى الدفع مسبقاً.
- **نقطة جديدة (الوكيل):** `POST /api/v1/agent/renewal-requests/:id/payment-confirm`
  Body: `{received:true}` → يضبط `confirmed_by_agent=true, confirmed_at` ويُشعر المشترك (`paymentRecorded`).
- **قائمة طلبات الوكيل**: تضمين `payment` ضمن كل `renewal-request`.
- **تقييد RADIUS**: الملخّصات/الدعوات للمشتركين من مصدر RADIUS فقط (يُفرض أيضاً من جهة وكيل نت؛ البوابة تثق بما يُنشَر).
- **النشر:** عبر مسار نشر البوابة المعتمد (صورة محلية → TAR → scp + replace-gateway.sh).

### 7.ب) تطبيق وكيل نت (NetAgent) — Phase 1
- **حفظ رقم حساب Qi**: حقل في شاشة إعدادات البوابة → `SubscriberPortalClient.setMasterAccount(value)` (PUT `portal-settings`).
- **قصر البوابة على RADIUS**: في `SubscriberPortalSync._run` ودعوة المشترك، استثناء `source ∈ {ftth, fiberx, earthlink}` — نشر/دعوة لمشتركي RADIUS فقط.
- **عرض ادّعاء الدفع**: في `subscriber_portal_requests_screen.dart` إظهار `payment.reference` (+ الوصل إن وُجد) وزر **«تأكيد الدفع»** → `payment-confirm`.
- **بوّابة ناعمة**: تنبيه الوكيل إن فعّل قبل تأكيد الدفع (دون منع صارم — قراره).
- `PortalRenewal`: إضافة حقول `payment*` وملصق حالة الدفع.

### 7.ج) تطبيق مشترك نت — Phase 2
- **شاشة الدفع** بعد إنشاء/فتح طلب تجديد: عرض `agent.masterAccount` كنصّ **قابل للنسخ** + المبلغ (`quotedPrice`) + زر «نسخ» + زر «افتح سوبر كي» (إن توفّر) + حقل **رقم التحويل** + زر **«دفعت»** → `payment-claim`.
- **حالة الدفع** في `renewal_details_screen`: «بانتظار تأكيد الوكيل» → «تم تأكيد الدفع» → «تم التجديد».
- عرض خطوة الدفع **فقط** عند وجود `masterAccount` (الوكيل فعّلها).
- `RenewalRequest` + العقد: قراءة `payment`.

## 8. الأمان ومنع الاحتيال
- لا تفعيل إلا بعد **تأكيد الوكيل** يدوياً استلام المبلغ.
- رقم تحويل إلزامي + وصل اختياري لكل ادّعاء، وادّعاء واحد لكل طلب مفتوح.
- البوابة ترفض الوكيل غير الفعّال (قاعدة R1 القائمة).
- لا يُطبع أي رقم حساب/اعتماد في السجلات.

## 9. خطة التنفيذ على مراحل (كل مرحلة تُختبر وتُعتمد وتُنشر وحدها)
- **Phase 0 — البوابة:** الحقول + النقطتان + النشر. (بدونها لا يعمل شيء.)
- **Phase 1 — وكيل نت:** حفظ Qi + تقييد RADIUS + عرض/تأكيد الدفع.
- **Phase 2 — مشترك نت:** شاشة الدفع + حالات الدفع. ثم رفع نسخة Play.

## 10. أسئلة مفتوحة (للحسم قبل Phase 0)
1. **تخزين الوصل:** الاكتفاء برقم التحويل أولاً (كفكرة «الرقم إثبات»)، أم رفع صورة من البداية (يلزم مخزن ملفات للبوابة)؟
2. **البوّابة قبل التفعيل:** تنبيه ناعم (يسمح بالتفعيل) أم منع صارم حتى تأكيد الدفع؟
3. **مكان حفظ رقم Qi:** شاشة إعدادات البوابة في وكيل نت — هل حقل واحد يكفي، أم رقم حساب + اسم صاحب الحساب للطمأنة؟
